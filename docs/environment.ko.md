# 클라우드 환경 사용법

## 2026-10-30 점검 및 게시 실패 진단

현재 인스턴스는 running 상태이며 플랫폼 상태의 failure는 null이다. 게시 실패 진단 기록은 조회되지 않았다. UI의 ‘설정은 저장되어 있습니다. 다시 게시해 보세요’는 구체적인 원인을 포함하지 않아 원인을 확정할 수 없다. 저장된 설치 절차·단위 테스트 6개·브라우저 테스트 18개는 다시 통과했고 Vercel API 인증도 성공했다.

이 작업에서 내려받은 npm/npx CLI 다운로드 캐시 약 1.1GB를 정리해 스냅샷 대상 크기를 줄였다. 앱 소스·설치된 의존성·인증 설정은 보존했다. 이는 크기를 줄이는 조치이며 캐시가 게시 실패의 원인으로 입증된 것은 아니다.

웹 서비스는 개발 환경 게시와 별도로 공식 Vercel API를 통해 배포했고 READY 및 공개 접속을 확인했다: https://viral-lovat.vercel.app/

클라우드 프록시형 인증 값은 CLI의 토큰 형식 검사에서 거절되므로 `python3 scripts/deploy-vercel.py`로 재배포한다. 토큰을 추출하거나 새 토큰을 중복 발급할 필요는 없다. 공개 배포 파일을 TLS 검증이 켜진 프록시 전송으로 읽어 모바일·데스크톱 Chromium에서 두 사람 응답·비교·결과 회신·새로고침을 확인했다. 브라우저 직접 프록시 연결은 로컬 CA 신뢰 문제로 실패했으며 인증서 검증을 끄지 않았다. 실제 기기·메신저 공유 UI 검증은 별도다.

## 웹 앱 구현 후 현재 작업 방법

2026-10-29 사용자 요청으로 ‘취향 싱크’ 정적 웹 앱을 구현했다. 아래 초기 기록의 ‘문서만 있는 상태’는 과거 기록이다. 현재 실행은 이 절을 따른다.

기존 `/workspace/viral`을 사용한다. 사용자가 명시적으로 요청하지 않는 한 worktree를 만들지 않는다. Node.js 22 이상이 필요하며 현재 머신과 CI는 Node.js 24를 사용한다.

```sh
cd /workspace/viral
npm ci --cache /workspace/.npm-cache
npm test
npm run build
npm start
```

기본 포트는 3000이며 `PORT`로 바꿀 수 있다. `dist/`의 파일을 제공한다. 기본 페이지와 `app.js`의 200 응답을 확인하고 브라우저에서 실제 문항 완료와 결과를 검증한다.

브라우저 검증은 빌드 후 `npm run test:e2e`를 실행한다. 포트 3100의 테스트 서버를 자동 시작·정리한다. 시스템 Chromium이 없다면 `npx playwright install chromium`을 먼저 실행한다. `/usr/bin/chromium`은 자동 사용하며 다른 경로는 `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`로 지정한다.

현재 인스턴스에서 단위 테스트 6개 및 모바일·데스크톱 Chromium 기능 테스트 18개를 통과했다. 두 사람의 응답과 결과 회신, Vercel용 루트 경로에서의 초대 링크, 빌드 시 공유 이미지 주소, 이전 질문, 공유 취소, 복사 거절, 깨진 링크, 로컬 저장소 거절·삭제, 정적 파일 응답을 확인했다. 모바일 검증은 Chromium 에뮬레이션이며 실제 iOS Safari 검증이 아니다. 운영체제 공유 UI와 실제 메시지 발송은 테스트에서 모의 처리했다.

앱의 런타임 API 키·DB·로그인은 필요 없다. `dist/`, `node_modules/`, `test-results/`는 생성물이며 Git에서 제외한다. 살아 있는 개발 서버가 새 클라우드 작업에 유지된다고 가정하지 않는다.

GitHub Pages 설정·상태 확인에 필요한 `api.github.com`과 공개 사이트 확인용 `planndoit.github.io`를 환경 허용 도메인 초안에 추가했다. 현재 인스턴스의 GitHub API 요청은 프록시 403으로 차단되어 있었다. 초안 저장은 현재 네트워크 반영과 다르므로 설정 적용 후 해당 작업을 재시도한다. 인증 값을 출력하거나 우회하지 않는다.

[배포 안내](deployment.ko.md)에 Vercel 배포·검증 절차가 있다. 이후 사용자 요청으로 배포 대상을 Vercel로 변경했다. `vercel.json`은 정적 빌드 결과 `dist/`를 게시한다. Vercel CLI 65.7.0의 인증 조회는 로그아웃 상태였으며 로그인 없는 `--temporary` 배포 옵션을 확인했다. Vercel 접근용 `api.vercel.com`, `vercel.com`, 테스트 호스트용 `*.vercel.app`도 허용 도메인 초안에 추가했다. 실제 반영 전에는 접근이 제한될 수 있다. 클라우드 환경의 Publish는 스냅샷 게시이며 웹 앱의 공개 배포와 별개다.

## 현재 준비된 작업

`/workspace/viral`은 문서 리서치·기획 저장소다. 문서는 GitHub에서 읽으며 설치, 실행 서버, 외부 서비스, DB, API 키가 필요하지 않다. 아직 서비스 코드를 구현하거나 배포하지 않았다.

기존 클라우드 체크아웃을 그대로 사용한다. 각 작업은 이미 격리되어 있으므로 사용자가 명시적으로 요청하지 않는 한 별도 Git worktree를 만들지 않는다.

## 도구와 네트워크

- 현재 인스턴스에서 Git 2.52.0, Node.js 24.19.0, npm 11.9.0, Python 3.12.14를 확인했다. 앱의 버전 핀을 지정한 것은 아니다.
- GitHub 인증은 플랫폼 HTTPS Git 프록시를 사용한다. 토큰을 파일에 넣거나 로그에 출력하지 않는다.
- 네트워크는 제한 모드이며 패키지 관리자 프리셋을 사용한다. GitHub 및 raw.githubusercontent.com의 필요한 읽기를 확인했다.
- NYT, Neal.fun, Pudding, Spotify Newsroom 등으로의 요청은 프록시 403으로 제한되었다. 이를 해당 서비스의 장애나 인증 실패로 해석하지 않는다.
- 원문 후속 조사가 필요하면 환경 설정에 필요한 도메인만 추가한다. 이번 문서 작업에는 추가 비밀값이나 네트워크 정책 변경이 필요하지 않았다.

## 시작과 검증

```sh
cd /workspace/viral
git status --short
git ls-files
git ls-remote origin refs/heads/main
```

문서를 수정할 때는 내부 상대 링크의 대상이 존재하는지 확인하고, 관찰한 사실·제품 해석·아직 검증하지 않은 가설을 구분한다. 설치·빌드·테스트 명령은 아직 없으며 문서 검증을 애플리케이션 테스트 통과로 표현하지 않는다.

## 다음 개발 작업

사용자가 서비스 구현을 요청하면 [MVP 제안](mvp-proposal.ko.md)을 출발점으로 질문·공유·비교 흐름을 만든다. 그때 선택한 기술 스택의 lockfile과 실제 빌드·테스트 명령을 추가하고 설치 및 시작 설정을 갱신한다. 라이브 프로세스는 클라우드 스냅샷에 유지된다고 가정하지 않는다.

## 설정 저장과 게시

환경 초안에는 실제 체크아웃 위치·커밋과 문서 작업 시작 안내를 저장한다. 의존성이 없으므로 설치 스크립트는 만들지 않는다. 초안 저장은 현재 머신에 명령을 실행하거나 환경을 게시하는 동작이 아니다. 설정 검토·저장 및 Publish는 환경 UI에서 사용자가 진행한다. 새 작업의 스냅샷 복원은 별도 확인이 필요하다.
