# 첫 실험: 우리 둘 취향 싱크

상태: 2026-10-29 최초 제안. 이후 사용자 요청으로 v1 웹 앱을 구현했다. 아래는 최초 설계 가설이며 현재 실행 방법은 [README](../README.md), 배포 확인 방법은 [배포 안내](deployment.ko.md)를 따른다. 실제 사용 시간·공유율·사용자 반응은 아직 검증하지 않았다.

## 한 문장

“6개만 골라봐. 우리 어디서 통하는지 알려줄게.”

혼자 1분 안팎으로 답하고 링크를 친구에게 보낸다. 친구도 답하면 ‘같은 선택 4/6’과 다른 두 선택이 한 화면에 나온다. 완료 시간은 제품 목표이며 측정값이 아니다. 성격·궁합의 과학적 진단으로 표현하지 않는다.

## 핵심 가설

친구는 다른 사람의 성향표를 보는 것보다, **내 선택을 더하면 우리 둘의 결과가 나오는 링크**에 참여할 이유가 크다. 이 가설이 맞는지는 실제 완료와 공유 유입을 측정해 판단한다.

## 흐름

1. **시작:** ‘6개 고르면 친구와 취향 비교 · 약 1분 · 가입 없음’. 바로 시작 버튼.
2. **선택:** 일상적인 두 선택지 6개. 진행도 2/6을 보여주고 뒤로 가기를 지원.
3. **혼자 완료:** 내 선택 요약과 ‘친구랑 비교하기’. 친구에게 보내야만 개인 결과를 볼 수 있는 구조는 쓰지 않는다.
4. **전달:** Web Share를 우선 제공하고, 링크 복사·텍스트 선택을 대안으로 제공.
5. **친구 유입:** ‘친구와 같은 질문 6개에 답해보세요’. 먼저 친구 답을 보여주어 선택을 유도하지 않는다.
6. **비교:** ‘같은 선택 4/6’과 항목별 비교. 불일치를 비난하지 않고 ‘같이 여행 가면 여기서 회의 필요’처럼 가벼운 대화 소재 제공.
7. **다음 행동:** ‘내 링크 만들어 다른 친구와 비교’. 원래 보낸 사람도 결과를 원하면 받은 친구가 비교 링크·카드를 돌려보낼 수 있도록 한다. 자동 알림은 첫 범위에서 제외.

## 질문 초안

| 상황 | A | B |
| --- | --- | --- |
| 약속 없는 토요일 | 일단 나가서 생각 | 집에서 충전 |
| 여행 첫날 | 계획표대로 착착 | 눈에 띄는 곳부터 |
| 친구에게 웃긴 일 생김 | 전화로 실시간 중계 | 짤과 메시지로 중계 |
| 카페에서 주문 | 늘 먹던 최애 | 처음 보는 신메뉴 |
| 갑자기 두 시간 여유 | 친구 불러 수다 | 혼자 취미 몰입 |
| 같이 영화 고를 때 | 편하게 웃을 작품 | 끝나고 토론할 작품 |

이 질문들은 검증되지 않은 초안이다. 정답·우열 없는 문장으로 다듬고, 같은 성향만 반복 측정하지 않는지 사용성 인터뷰에서 확인한다. 관계 갈등·외모·건강·소득 같은 민감한 주제는 첫 실험에 넣지 않는다.

## 결과와 공유 문구

> 우리 같은 선택 4/6 🎯
> 여행은 계획파, 카페에서는 신메뉴파.
> 영화 취향은 달라서 추천이 더 재밌겠는데?
> 너도 6개만 골라봐: {공유 링크}

개인 완료 화면은 ‘내 답변 6개’, 비교 화면은 ‘우리 같은 선택 4/6’로 구분한다. 모집단 없이 ‘상위 3%’, ‘드문 조합’ 같은 수치는 만들지 않는다. 6개 중 일치 수만 보여주며 궁합 점수로 일반화하지 않는다.

## 첫 구현 범위

**필수:** 모바일 반응형 웹, 고정된 6문항, 질문 세트 버전, 개인 결과, 초대 링크, 비교 결과, 링크 복사, 공유 취소 처리, 키보드 조작과 읽기 쉬운 대비, 잘못된 링크의 복구 화면.

**후순위:** 결과 이미지 저장, 카카오 전용 SDK, 로그인, 순위표, 실시간 방, 푸시 알림, AI 생성 결과, 결제. 일반 링크 공유만으로 먼저 검증하고 SDK·API 키는 실제 필요가 생기면 추가한다.

첫 화면에서는 프레임워크나 데이터 저장 같은 구현 설명 대신 예상 시간과 할 일을 보여준다.

## 가장 작은 구현 선택

- 정적 웹으로 시작한다. 프레임워크는 개발 작업에서 결정하며 이 문서 작업에서는 의존성을 미리 추가하지 않는다.
- 답변 6비트와 질문 세트 버전을 URL fragment에 인코딩하면 초기 DB 없이 비교할 수 있다. 이는 암호화가 아니며 링크를 받은 사람은 내용을 해독할 수 있다. 이름·연락처·민감한 응답은 넣지 않는다.
- fragment는 일반 HTTP 요청과 서버 OG 렌더링으로 전달되지 않는다. 따라서 초기 미리보기는 공통 이미지·문구를 쓴다. 답변별 OG 카드는 별도 서버 설계가 필요하다.
- 클라이언트 코드와 분석 SDK는 fragment를 읽을 수 있으므로 분석에 전체 URL·답변을 수집하지 않는다. 로컬 저장은 질문 버전과 함께 다루고 초기화 버튼을 제공한다.
- 초대 데이터의 길이·형식·버전을 검증한다. 답변을 URL로 전달하는 구조는 부정행위 방지나 비밀 투표에 적합하지 않지만 이 놀이에는 경쟁 보상이 없다.
- 원래 보낸 사람에게 자동으로 결과가 도착하지 않는다. 첫 실험은 친구가 결과를 되돌려 보내는 흐름으로 검증하고, 자동 회수 필요성이 확인되면 저장소와 익명 토큰을 설계한다.

## 검증할 행동과 지표

서버나 분석 도구가 아직 없으므로 아래는 계측 설계다. 현재 수집 중인 지표가 아니다.

| 지표 | 정의 | 알 수 있는 것 / 한계 |
| --- | --- | --- |
| 시작률 | 질문 시작 세션 / 시작 화면 도달 세션 | 메시지가 행동을 유도하는가 |
| 완료율 | 6문항 완료 세션 / 질문 시작 세션 | 흐름이 길거나 이해하기 어려운가 |
| 공유 행동률 | 공유 API 완료 또는 링크 복사 성공 세션 / 최초 개인 완료 세션 | 전달 의향의 대리 지표. 실제 발송·수신을 뜻하지 않음 |
| 초대 유입 완료율 | 비교 결과 도달 세션 / 유효 초대 링크 진입 세션 | 받은 사람이 가치를 얻는가 |
| 후속 생성률 | 새 개인 초대 링크를 만든 초대 유입 세션 / 비교 완료 세션 | 공유가 다음 생성으로 이어지는가 |

이벤트 초안: `landing_view`, `quiz_start`, `quiz_complete`, `share_success`, `copy_success`, `invite_open`, `compare_complete`, `own_invite_created`. `share_success`는 운영체제·브라우저별 의미 차이가 있으므로 복사 성공과 분리한다. 취소·오류를 성공으로 세지 않는다. 브라우저별 공유 지원도 따로 기록한다.

코호트는 일반 유입과 초대 유입을 분리한다. 브라우저 세션 기반 중복 제거는 사람 수와 다르며 여러 기기·재방문으로 오차가 생긴다. 기기 지문으로 보정하지 않는다. 초대 ID를 쓴다면 답변과 분리한 무작위 식별자와 보존 기간을 먼저 정한다.

바이럴 계수는 이론적으로 ‘사람당 실제 초대 수 × 초대받은 사람의 참여 전환율’이지만, 공유 버튼 클릭과 복사 성공만으로 실제 초대 수를 알 수 없다. 첫 실험에서는 바이럴 계수를 주장하지 않고 초대 유입부터 후속 생성까지의 퍼널을 관찰한다.

## 첫 사용자 실험

1. 5–8명에게 설명 없이 모바일로 써보게 하고, 멈춘 화면과 결과를 이해하는지 확인한다.
2. 별도로 동의한 소규모 친구 그룹 3–5개에서 링크가 어떻게 전달되는지 관찰한다. 친구에게 공유하도록 강제하지 않는다.
3. ‘누구에게 왜 보내고 싶었는지’, ‘받았을 때 왜 열었는지’, ‘결과에서 무슨 얘기를 했는지’를 묻는다.
4. 조기 판단 기준으로 완료율 70%, 공유 행동률 20%를 가설 목표로 둘 수 있다. 이는 업계 기준이 아니며 소표본으로 통계적 성공을 선언하지 않는다. 분모와 실제 건수를 함께 기록한다.
5. 완료는 높고 초대 유입 완료가 낮으면 초대 문구·첫 화면부터 수정한다. 비교는 완료하지만 다음 링크 생성이 없다면 관계 결과가 대화의 소재였는지 확인한다.

첫 목표는 바이럴을 선언하는 것이 아니라 **사용자가 자발적으로 한 명에게 보내고, 받은 사람이 끝까지 해보는지** 확인하는 것이다.
